## What is fixed

Two reports from Windows, both of them things you could see and neither of
them visible on Linux.

### Quitting the application now leaves nothing running

**The symptom.** You quit IXD and `ixd.exe` was still in Task Manager. Ending
the task did not settle it either — it came back, and the only thing that
actually stopped it was removing the extension from the browser.

**What it actually was.** That process was not the application. It was the
*native messaging host* — the small relay the browser spawns to talk to IXD.
On Windows the browser is pointed straight at `ixd.exe` for that job (a `.bat`
wrapper would put `cmd.exe` in the middle of a binary pipe), so the relay runs
under the application's own name and nothing in a task list can tell the two
apart. The browser keeps that process alive for exactly as long as its
connection is open, and the extension never closed one — the in-page panel kept
the connection busy, so the relay outlived the application it relays to.

**The fix.** The extension lets the connection go when there is nothing to
relay: five seconds of quiet, and at once when the relay reports the
application is not running. That answer is then believed for fifteen seconds,
so the extension's own background polling costs no process at all. A request
still in flight holds the connection until it is answered. Anything *you* asked
for — a download, a click on the panel — still starts the application, which is
the whole point of the bridge.

### Progress shows on the Windows taskbar

**The symptom.** Linux drew a progress bar on the application's icon while a
download ran. Windows drew nothing.

**What it actually was.** Windows paints progress onto a *window's taskbar
button*, and IXD was painting onto the main window — which is hidden whenever
the browser started the application, or whenever you closed it to the tray.
That is exactly when the icon is the only thing there is to look at. The call
succeeded and painted a button that did not exist. Linux never showed this
because its desktop draws progress for the *application*, not for a window.

**The fix.** Every window that is actually on the taskbar is drawn on now,
worked out afresh on each update — so a download window that opens on its own
carries the bar even with the main window down, and a window that opens partway
through a transfer gets the bar rather than being skipped.

The Windows side also stopped failing in silence. If the desktop refuses,
the reason goes in the **Log** (toolbar → Log → Copy) instead of leaving you
with an empty taskbar and nothing to report.

> **Honest boundary.** These two are reasoned and tested as far as a Linux
> machine can test them — there is no Windows hardware here. The offline tests
> prove the relay is released and prove which windows are drawn on; they cannot
> prove Windows paints them. If the bar still does not appear, the Log will now
> say why, and that report is genuinely useful.

### Also

* The version number is written in one place. A release whose files were named
  after the *previous* release is a mistake this project has already made once,
  so `build.py`, the macOS bundle and both extension manifests read it from the
  application now, and a build stops rather than shipping a manifest that
  disagrees.
